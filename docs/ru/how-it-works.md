# Как работает драйвер

*[In English](../en/how-it-works.md)*

Какие объекты держит программа, как проходит сессия с картой, поле, время, память и задачи. Функции, названные здесь, по
отдельности описаны в [справочнике API](api.md).

## Три объекта

```text
pn5180_spi_t      the SPI host and the PN5180 as a device on it
    ^
pn5180_t          one PN5180: pins, buffers, field, timing, the state of the selected card
    ^
pn5180_proto_t    one RF protocol on that PN5180: ISO14443A or ISO15693
```

- **`pn5180_spi_t`** — результат `pn5180_spi_init()`, которая сама инициализирует шину, или `pn5180_spi_attach()`,
  которая добавляет PN5180 на шину, уже инициализированную программой и общую с другими устройствами.
- **`pn5180_t`** — результат `pn5180_init()`: она сбрасывает PN5180, ждёт, пока он загрузится, проверяет его прошивку
  (3.4 или новее) и держит два буфера по 512 байт, пригодных для DMA, для передач по SPI. Структура публичная, потому
  что драйвер разбит на несколько исходных файлов; программа обращается с ней как с дескриптором. Программа читает поля
  `iso14443_last_auth_status` (почему не прошла аутентификация MIFARE Classic, см. [Карты
  ISO14443A](iso14443a.md#аутентификация)) и `firmware_version`; `timeout_ms` описано в разделе [Время
  и ожидания](#время-и-ожидания).
- **`pn5180_proto_t`** — результат `pn5180_14443_init()` или `pn5180_15693_init()`. Оба объекта могут жить на одном
  PN5180 и работают по очереди: `setup_rf()` одного протокола загружает его конфигурацию RF вместо конфигурации другого.

## Два протокола

| | ISO14443A | ISO15693 |
|---|---|---|
| Создание | `pn5180_14443_init(pn5180, max_cards)` | `pn5180_15693_init(pn5180, PN5180_15693_26KASK100)` |
| Карты | MIFARE Classic, Plus, Ultralight, NTAG21x, DESFire и другие карты ISO14443-4, телефоны | ICODE SLIX и другие метки дальнего действия (vicinity) |
| Дальность | несколько сантиметров | больше |
| Аутентификация | ключи MIFARE Classic (`authenticate`) | нет |
| NDEF | Type 2, MIFARE Classic, Type 4 | Type 5 |
| Заголовок | `pn5180-14443.h` | `pn5180-15693.h` |

## Объект протокола

Каждая операция с картой проходит через колбэки объекта протокола, и набор колбэков у обоих протоколов один и тот же:

| Колбэк | ISO14443A | ISO15693 |
| -------- | --------- | -------- |
| `setup_rf(proto)` | конфигурация RF 00h (106 кбит/с), включение поля | конфигурация, переданная в `pn5180_15693_init()`, включение поля |
| `get_all_uids(proto)` | REQA, антиколлизия на всех уровнях каскада, HLTA для каждой карты | инвентаризация с разрешением коллизий, Stay Quiet для каждой метки |
| `select_by_uid(proto, uid)` | WUPA и SELECT на каждом уровне каскада; RATS для карты ISO14443-4 | Select (адресный) |
| `detect_card_type_and_capacity(pn5180, uid, &blocks, &size)` | по SAK, затем GET_VERSION для семейства Ultralight | Get System Information |
| `authenticate(proto, key, key_type, uid, block)` | Crypto1 MIFARE Classic; для Ultralight, NTAG и карт ISO14443-4 сразу `true` | `NULL`: недоступен |
| `block_read(proto, block, buf, len)` | READ (30h), 16 байт; READ BINARY на карте ISO14443-4 | Read Single Block, выше блока 255 — Extended |
| `block_write(proto, block, buf, len)` | WRITE (A2h) 4-байтной страницы или MIFARE WRITE (A0h) 16-байтного блока | Write Single Block, выше блока 255 — Extended |
| `halt(proto)` | HLTA; S(DESELECT) для карты ISO14443-4 | Reset to Ready (выбранной метке) |

Обратите внимание на исключения: `detect_card_type_and_capacity()` принимает `pn5180_t`, а не объект протокола;
`block_write()` возвращает `int`, 0 при успехе и отрицательное значение при ошибке, а остальные возвращают `bool`;
у объекта ISO15693 нет `authenticate`, поэтому на объекте, который может быть любым из двух, указатель проверяют перед
вызовом.

Объект протокола выделяется в куче и освобождается через `free()`.

## Сессия с картой

1. **`setup_rf()`** загружает конфигурацию RF протокола и включает поле.
2. **`get_all_uids()`** перечисляет карты. Каждую найденную карту ISO14443A он останавливает, каждую метку ISO15693
   заставляет замолчать, чтобы могли ответить следующие; выбранной не остаётся ни одна. См. [Поиск карт](polling.md).
3. **`select_by_uid()`** будит одну карту и выбирает её. Для карты ISO14443-4 сюда входит активация (RATS).
4. **`detect_card_type_and_capacity()`** заполняет `subtype`, `block_size` и `blocks_count` в `pn5180_uid_t`. Он
   возвращает `true`, когда после неё карту нужно выбрать снова; так бывает у семейства Ultralight.
5. **Доступ к блокам, аутентификация, NDEF и APDU** работают с выбранной картой.
6. **`halt()`** завершает сессию: HLTA для карт ISO14443-3, S(DESELECT) для карт ISO14443-4, Reset to Ready для меток
   ISO15693. Остановленную карту ISO14443A `select_by_uid()` находит снова, а `get_all_uids()` — только после того, как
   поле выключали.

Выбранная карта ISO14443A не отвечает на новый `select_by_uid()`: сначала нужен `halt()`. Исключение, и опасное, —
карта, оставленная в своей сессии ISO14443-4: она не замечает пробуждения и активации следующей карты, но отвечает на
каждый I-block, в том числе на те, что предназначены той карте. Поэтому `select_by_uid()` и `get_all_uids()` сами
закрывают такую сессию через S(DESELECT), прежде чем послать что-то ещё.

Несколько семейств карт выходят из выбранного состояния после ошибки: Ultralight и NTAG — после любого NAK, например на
чтение за последней страницей, MIFARE Classic — после отказа в аутентификации. После такой ошибки перед следующей
командой нужны `halt()` и снова `select_by_uid()`.

## pn5180_uid_t

Опрос возвращает массив `pn5180_uid_t`, по элементу на карту. Программа хранит элемент и передаёт его в остальные
колбэки:

| Поле | Кто заполняет | Значение |
| ----- | --------- | ------- |
| `uid`, `uid_length` | опрос | UID в том порядке, в каком его посылает карта: 4, 7 или 10 байт у ISO14443A; 8 у ISO15693, младшим байтом вперёд, так что `uid[7]` — это `E0` |
| `sak`, `atqa` | опрос, `select_by_uid()` | только ISO14443A: SAK последнего уровня каскада, ATQA первым байтом вперёд |
| `agc` | опрос | значение AGC приёмника, когда карта отвечала: чем меньше, тем сильнее сигнал и ближе карта |
| `subtype` | `detect_card_type_and_capacity()` | тип карты, `pn5180_card_type_t`; после опроса — `PN5180_MIFARE_UNKNOWN` |
| `blocks_count`, `block_size` | `detect_card_type_and_capacity()` | память: число блоков или страниц и их размер в байтах |

Функции NDEF выбирают схему размещения NDEF по `subtype`, поэтому сначала нужно определить тип карты. Изменить `subtype`
перед `select_by_uid()` — способ выбрать сторону ISO14443-4 у карты, у которой есть обе, см. [Карты с MIFARE Classic
и ISO14443-4 сразу](iso14443a.md#карты-с-mifare-classic-и-iso14443-4-сразу).

## ВЧ-поле

- **`setup_rf()`** оставляет поле как есть, когда его собственная конфигурация RF уже загружена и поле включено; он
  проверяет, что поле действительно включено, и включает его снова, если оно пропало. Карты, которые прошлый опрос
  остановил или заставил замолчать, такими и остаются. Если загружена конфигурация другого протокола, он выключает поле
  на 5,1 мс, загружает свою и включает поле.
- **Сброс поля** возвращает каждую карту в состояние покоя: `pn5180_set_rf_off()`, затем не меньше
  `PN5180_RF_OFF_TIME_US` (5,1 мс; 5 мс мало), затем `setup_rf()`. Цикл, который хочет видеть одни и те же карты на
  каждом проходе, делает так перед каждым опросом, как [первая программа](getting-started.md#3-первая-программа).
- **Защитное время.** После включения поля драйвер ждёт 5,1 мс перед первой командой, чтобы карты успели получить
  питание. Его меняет `pn5180_set_rf_guard_time_us()`; меткам ISO15693 нужна 1 мс.
- **Защита от столкновения полей (RFCA)** по умолчанию включена: PN5180 не включает своё поле, пока есть чужое поле,
  и `setup_rf()` не удаётся. После `pn5180_set_rfca(pn5180, false)` поле включается в любом случае.
- Выключение поля через `pn5180_set_rf_off()`, `pn5180_reset()` или `pn5180_recover()` завершает все сессии: сессия
  ISO14443-4 помечается закрытой, и карты нужно выбирать заново.

## Время и ожидания

**Тайм-ауты карт.** Ожидание ответа карты отсчитывает Timer1 PN5180: он запускается в конце передачи и останавливается,
когда начинается приём. Поэтому об отсутствующей карте драйвер сообщает за миллисекунды, независимо от загрузки хоста.
У каждой команды свой тайм-аут, в несколько раз больше того, что допускают стандарты, потому что слишком короткий
тайм-аут ломает работу исправной карты:

| Команда | Тайм-аут |
| ------- | ------- |
| ISO14443A REQA, WUPA, антиколлизия, SELECT | 5 мс |
| RATS | 20 мс |
| MIFARE READ, GET_VERSION, ACK после команды записи | 10 мс |
| ACK после программирования данных | 20 мс |
| ISO15693 Inventory, Select, Read, Get System Information, Reset to Ready | 10 мс |
| ISO15693 Write Single Block | 40 мс |
| I-block ISO14443-4 | время ожидания кадра, которое карта объявляет в своём ATS, с продлением, когда карта его просит |

`pn5180_set_hw_rx_timeout(pn5180, false)` заменяет Timer1 тайм-аутом на стороне хоста, который медленнее сообщает об
отсутствующей карте; это помогает отличить неполадку таймера от неполадки в ВЧ-тракте.

**Ожидания PN5180.** `pn5180_t.timeout_ms`, по умолчанию 500 мс, ограничивает только ожидания самого PN5180: BUSY,
состояния приёмопередатчика, включения или выключения поля, `pn5180_wait_for_irq()`. Это не тайм-аут карты.

**Конец обмена.** С [пином IRQ](hardware.md#пин-irq) драйвер спит, пока PN5180 не сообщит о конце обмена. Без него
драйвер читает регистр состояния IRQ по SPI: первые 5 мс — подряд, без пауз, затем раз в миллисекунду, отпуская
процессор в промежутках.

**Собственные ожидания драйвера** (защитное время, время, на которое выключается поле при повторной настройке протокола,
стартовое защитное время кадра у карт ISO14443-4, сброс) спят на таймере высокого разрешения (`esp_timer`) объекта
`pn5180_t`: процессор в это время свободен, а ожидание опаздывает самое большее на несколько десятков микросекунд и
никогда не заканчивается раньше срока.

**`pn5180_delay_ms()` и `pn5180_delay_us()`** не связаны с устройством: они спят целыми тиками RTOS, а остаток, до
одного тика, ждут в активном цикле. Для паузы, которой не нужна точность, например между опросами, подходит
`vTaskDelay()`.

## Память

| Что | Где | Размер | Чем освобождается |
| ---- | ----- | ---- | ----------- |
| `pn5180_spi_t` | куча | небольшой | `pn5180_deinit()` или `pn5180_spi_deinit()`, если `pn5180_init()` не удалась |
| `pn5180_t` и её буферы | куча, буферы пригодны для DMA | два буфера по 512 байт и структура | `pn5180_deinit()` |
| `pn5180_proto_t` | куча | небольшой | `free()` |
| `pn5180_uids_array_t` опроса | куча | по одному `pn5180_uid_t` на карту | `free()` |
| сообщение NDEF, прочитанное с карты | куча | см. [память NDEF](ndef.md#память) | `pn5180_ndef_free_parsed_message()` |

Некоторые вызовы ещё выделяют память на время своей работы и освобождают её перед возвратом:
`pn5180_14443_4_transceive()` — около 0,3 КБ под состояние обмена, функции NDEF — свои буферы чтения и записи. Функции
сборки записей, утилиты APDU и `pn5180_ndef_decode_message()` ничего не выделяют и работают в буферах вызывающего.

### Стек задачи

Буферы SPI живут в `pn5180_t`, но код протоколов держит буферы кадров на стеке. По замерам `-fstack-usage` GCC и графа
вызовов на ESP32 (ESP-IDF 5.5, `-Og` — значение по умолчанию в новом проекте) кадры стека драйвера на его самых глубоких
путях складываются примерно в 1,5 КБ:

- чтение NDEF с MIFARE Classic, около 1,5 КБ: аутентификация держит буфер на 512 байт, чтобы после отказа опустошить
  приёмник;
- опрос ISO15693, около 1,5 КБ: инвентаризация держит свой стек поиска, 0,8 КБ, в одном кадре стека;
- чтение NDEF с Type 4, около 1,4 КБ: буфер READ BINARY и буферы блоков `pn5180_14443_4_transceive()`;
- выбор карты ISO14443-4, около 0,9 КБ вместе с буфером ATS; опрос ISO14443A, около 0,8 КБ.

Сверху добавляются драйвер SPI ESP-IDF, логирование и вызывающий код. Стек задачи, которая вызывает драйвер, выбирают
с учётом этого; цифры — это кадры стека драйвера, а не максимальная глубина стека работающей задачи.

## Задачи и блокировки

В драйвере нет блокировок: один `pn5180_t` нельзя использовать из двух задач одновременно. Два считывателя, каждый со
своим `pn5180_t`, могут работать в разных задачах, в том числе на одной шине SPI; создавать и удалять их нужно из одной
задачи.

Считывателям с близко расположенными антеннами всё равно приходится включать поле по очереди: каждый мешает картам
в поле другого, а с включённой защитой от столкновения полей (по умолчанию) считыватель не включает своё поле, пока
включено поле другого. Каждый цикл стоит заканчивать вызовом `pn5180_set_rf_off()`.

## Владение и время жизни

- `pn5180_spi_init()` и `pn5180_spi_attach()` возвращают выделенный в куче `pn5180_spi_t *`. `pn5180_spi_attach()`
  никогда не освобождает саму шину.
- `pn5180_init()` возвращает выделенный в куче `pn5180_t *`. Если вызов не удался, структура SPI остаётся нетронутой:
  можно повторить попытку или освободить её через `pn5180_spi_deinit()`.
- `pn5180_deinit(pn5180, true)` освобождает устройство, его устройство SPI и шину, если её создала `pn5180_spi_init()`;
  `pn5180_deinit(pn5180, false)` шину оставляет.
- `pn5180_14443_init()` и `pn5180_15693_init()` возвращают выделенный в куче `pn5180_proto_t *`; его освобождают через
  `free()` до `pn5180_deinit()`.
- `get_all_uids()` и функции `..._get_all_uids_ex()` возвращают выделенный в куче `pn5180_uids_array_t *`; его
  освобождают через `free()`.
- `pn5180_ndef_read_card_auto()`, `pn5180_ndef_read_from_selected_card()` и `pn5180_ndef_parse_message()` возвращают
  выделенный в куче `pn5180_ndef_message_parsed_t *`, который владеет копией сообщения; его освобождают через
  `pn5180_ndef_free_parsed_message()`.

## Результаты и ошибки

- Большинство функций возвращают `bool`. `block_write()` и `pn5180_mifare_block_write()` возвращают 0 при успехе
  и отрицательное значение при ошибке.
- Почему опрос ничего не вернул, он сообщает через `pn5180_poll_status_t`, см. [Статус
  опроса](polling.md#статус-опроса).
- Функции NDEF возвращают `pn5180_ndef_result_t`; `pn5180_ndef_result_to_string()` даёт текст для лога.
- Утилиты APDU возвращают `esp_err_t`.
- `pn5180_rf_transceive()` возвращает `pn5180_rf_result_t`, который различает тайм-аут, коллизию, ошибку приёма,
  переполнение и сбой транспорта.

Когда перестаёт отвечать сам PN5180 (опрос сообщает `PN5180_POLL_TRANSPORT_ERROR`), `pn5180_recover()` сбрасывает его
и восстанавливает конфигурацию RF и состояние поля, которые были до сброса. Карты нужно выбирать заново.

## Логирование

Драйвер пишет в лог с тегами ESP-IDF `PN5180` (слой считывателя), `pn5180-14443`, `pn5180-15693`, `pn5180-mifare`
и `pn5180-ndef`. Ошибки и предупреждения компилируются всегда; отладочные строки кода протоколов компилируются, только
когда в `include/pn5180-internal.h` определён `PN5180_DEBUG`, и тогда выводятся на отладочном уровне лога. Ключи MIFARE
никогда не попадают в лог.
