# NDEF

*[In English](../en/ndef.md)*

NDEF — формат NFC Forum для данных на метке: сообщение из записей, каждая из которых — URI, текст, MIME-объект или
тип, заданный приложением. Телефон читает его, когда касается метки. Драйвер читает NDEF по всем четырём известным ему
схемам размещения, записывает по двум из них, а также собирает и разбирает сообщения в памяти.

```c
#include "pn5180-ndef.h"
```

| Метка | Схема размещения | Чтение | Запись |
| ----- | ---------------- | ------ | ------ |
| Ultralight, NTAG | NFC Forum Type 2 | да | да |
| MIFARE Classic, MIFARE Plus на уровне безопасности 2 | схема MIFARE Classic (MAD) | да | нет |
| Карты ISO14443-4, телефоны | NFC Forum Type 4 | да | нет |
| Метки ISO15693 | NFC Forum Type 5 | да | да |

Не реализованы: форматирование чистой метки, запись NDEF на карты MIFARE Classic и Type 4.

## Чтение

```c
pn5180_ndef_message_parsed_t *msg = NULL;
pn5180_ndef_result_t result = pn5180_ndef_read_card_auto(proto, card, &msg);
if (result == PN5180_NDEF_OK) {
    for (size_t i = 0; i < msg->record_count; i++) {
        const pn5180_ndef_record_t *rec = &msg->records[i];
        char uri[256];
        const uint8_t *text;
        size_t text_len;
        char lang[64];
        if (pn5180_ndef_extract_uri(rec, uri, sizeof(uri)) > 0) {
            printf("URI: %s\n", uri);
        } else if (pn5180_ndef_extract_text(rec, &text, &text_len, lang, sizeof(lang), NULL)) {
            printf("Text (%s): %.*s\n", lang, (int)text_len, text);
        }
    }
    pn5180_ndef_free_parsed_message(msg);
} else {
    ESP_LOGW(TAG, "%s", pn5180_ndef_result_to_string(result));
}
```

`pn5180_ndef_read_card_auto()` выбирает схему размещения по `card->subtype`, поэтому карту нужно сначала выбрать и
определить её тип (`select_by_uid()`, `detect_card_type_and_capacity()` и второй `select_by_uid()`, если этого требует
определение типа). Функция не проверяет, какая карта выбрана: вызывающий сам выбирает ту карту, которую передаёт.

При успехе в `msg` лежат закодированное сообщение (`raw_data`, `raw_data_len`) и его записи (`records`,
`record_count`); фрагментированные (chunked) записи уже собраны. `pn5180_ndef_free_parsed_message()` освобождает всё
это.

### Результаты

| Результат | Значение |
| --------- | -------- |
| `PN5180_NDEF_OK` | сообщение прочитано и разобрано |
| `PN5180_NDEF_ERR_NO_NDEF` | карта работает, но не отформатирована под NDEF или не несёт сообщения |
| `PN5180_NDEF_ERR_UNSUPPORTED` | для этого типа карты здесь нет схемы размещения NDEF, или метка объявляет версию схемы размещения или условия доступа, которых драйвер не знает |
| `PN5180_NDEF_ERR_ACCESS_DENIED` | метка защищает своё сообщение от чтения |
| `PN5180_NDEF_ERR_PARSE_FAILED` | в метке или в сообщении есть противоречия |
| `PN5180_NDEF_ERR_READ_FAILED` | чтение не удалось, и после нового выбора карты тоже |
| `PN5180_NDEF_ERR_NO_MEMORY` | не удалось выделить память под сообщение |
| `PN5180_NDEF_ERR_INVALID_PARAM` | один из аргументов — `NULL` |

Проверки те же, что в библиотеке NXP для считывателей (NxpNfcRdLib).

Неудачное чтение выполняется ещё раз после нового выбора карты, потому что карты нескольких семейств после ошибки
выходят из выбранного состояния. `PN5180_NDEF_ERR_READ_FAILED` значит, что не удалась и вторая попытка. После этого
карта может быть не в выбранном состоянии: перед другими командами выберите её снова.

### Type 2: Ultralight и NTAG

Capability container — страница 3: магическое число E1h, версия схемы размещения, размер области данных, условия
доступа. TLV начинаются со страницы 4. Lock Control TLV и Memory Control TLV отмечают байты блокировки и
зарезервированные байты внутри области данных; чтение обходит их, так что сообщение продолжается за ними. Область
данных — та, которую объявляет capability container, но не больше памяти, найденной при определении типа. Метка без
GET_VERSION (первый Ultralight, NTAG203) определяется как Ultralight на 16 страниц, это догадка, поэтому для неё
размер задаёт только capability container.

Capability container со старшей версией, отличной от 1, или с условиями доступа, отличными от «чтение и запись» и
«только чтение», даёт `PN5180_NDEF_ERR_UNSUPPORTED`.

### MIFARE Classic

Сектор каталога (MAD, сектор 0, а на карте 4K ещё и сектор 16) перечисляет, какие секторы принадлежат какому
приложению; у секторов NDEF идентификатор приложения 03E1h.

- Сектор каталога открывается ключом MAD `A0 A1 A2 A3 A4 A5` или ключом по умолчанию `FF FF FF FF FF FF`. У карты,
  которая отвергает оба, нет общедоступного MAD: `PN5180_NDEF_ERR_NO_NDEF`. То же для MAD с неверным CRC и для карты,
  у которой секторы NDEF идут не подряд.
- Секторы NDEF открываются ключом NFC `D3 F7 D3 F7 D3 F7` или ключом по умолчанию. Секторы, которые отвергают оба,
  дают `PN5180_NDEF_ERR_ACCESS_DENIED`.
- Байт общего назначения (GPB) первого сектора NDEF (версия схемы размещения и доступ на чтение) проверяется, если
  сектор открыл ключ NFC. Сектор, который открывается только ключом по умолчанию, никогда не форматировался под NFC и
  хранит заводской байт 69h, который ничего не говорит об NDEF, поэтому он читается без этой проверки.
- Карта, которая не ответила на аутентификацию сектора каталога или сектора NDEF (на мгновение вышла из поля), и
  READ каталога, который не удался после того, как ключ MAD был принят, — это ошибки чтения: чтение повторяется после
  нового выбора. Карта, которая отвергла оба ключа сектора, во второй раз ответит так же, и повторно она не читается.
- NDEF TLV длиннее секторов, перечисленных в каталоге, даёт `PN5180_NDEF_ERR_PARSE_FAILED`.

### Type 4: карты ISO14443-4 и телефоны

Выбирается приложение NDEF схемы размещения 2.0 и новее (AID `D2 76 00 00 85 01 01`), как в библиотеке NXP для
считывателей, затем файл capability container E103h, затем файл NDEF, который он называет. У метки схемы размещения
1.0 другой AID, и она читается как `PN5180_NDEF_ERR_NO_NDEF`.

SELECT, который карта отклоняет словом состояния, даёт `PN5180_NDEF_ERR_NO_NDEF`; SELECT, в ответе на который нет
слова состояния, — ошибка чтения, и чтение повторяется. Файл NDEF, который capability container объявляет недоступным
для чтения, даёт `PN5180_NDEF_ERR_ACCESS_DENIED`. Сообщение Type 4 может быть длиной до 32 КБ, см. [Память](#память).

### Type 5: ISO15693

Capability container лежит в блоке 0 (4 байта, у большой метки 8), за ним идут TLV. Версия и условия доступа
проверяются так же, как у Type 2.

### Память

Сообщение читается с метки в один буфер в куче и разбирается в один блок памяти, который освобождает
`pn5180_ndef_free_parsed_message()`; в этом блоке ещё одна копия сообщения и по `pn5180_ndef_record_t` (24 байта на
ESP32) на каждую запись. Насколько всё это велико, решает метка; собственного предела драйвер не ставит.

Худший случай — карта Type 4 или телефон в роли такой карты: до 32 КБ сообщения, а 32 КБ самых маленьких возможных
записей (по 3 байта) занимают в пике около 320 КБ. Без PSRAM такое выделение памяти не удаётся, и чтение возвращает
`PN5180_NDEF_ERR_NO_MEMORY`; с PSRAM и `CONFIG_SPIRAM_USE_MALLOC` оно удаётся, и память остаётся занятой, пока
сообщение не освобождено. Метка Type 2 вмещает не больше примерно 900 байт, метка ISO15693 — обычно несколько КБ.

## Записи

```c
typedef struct {
    pn5180_ndef_tnf_t tnf;         /* Type Name Format */
    uint8_t           type_len;
    uint8_t           id_len;
    uint32_t          payload_len;
    const uint8_t    *type;
    const uint8_t    *id;
    const uint8_t    *payload;
} pn5180_ndef_record_t;
```

Запись указывает в память, которой не владеет: в разобранное сообщение, в буфер, из которого она декодирована, или в
буферы, переданные функциям сборки ниже.

`pn5180_ndef_get_record_type()` относит запись к одному из видов, которые знает драйвер:

| Вид | TNF и тип | Вспомогательная функция |
| --- | --------- | ----------------------- |
| `PN5180_NDEF_RECORD_TYPE_URI` | Well-known, `U` | `pn5180_ndef_extract_uri()` |
| `PN5180_NDEF_RECORD_TYPE_TEXT` | Well-known, `T` | `pn5180_ndef_extract_text()` |
| `PN5180_NDEF_RECORD_TYPE_SMARTPOSTER` | Well-known, `Sp` | `pn5180_ndef_decode_smartposter()` |
| `PN5180_NDEF_RECORD_TYPE_MIME` | Media type, например `application/json` | `type` и `payload` как есть |
| `PN5180_NDEF_RECORD_TYPE_EXTERNAL` | External, например `example.com:mytype` | `type` и `payload` как есть |
| `PN5180_NDEF_RECORD_TYPE_EMPTY` | Empty | нет |
| `PN5180_NDEF_RECORD_TYPE_UNKNOWN` | всё остальное | нет |

`pn5180_ndef_record_is_uri()`, `_is_text()` и `_is_smartposter()` отвечают на тот же вопрос для одного вида.

### URI

```c
char   uri[256];
size_t len = pn5180_ndef_extract_uri(rec, uri, sizeof(uri));
if (len >= sizeof(uri)) {
    /* truncated: len is the full length */
}
```

Код префикса из записи (`https://www.`, `tel:`, `mailto:` и остальные из определения записи URI) разворачивается.
Результат — длина всего URI без завершающего NUL, 0 для записи, которая не URI; в `uri` всегда попадает строка,
завершённая NUL, обрезанная, если результат равен `sizeof(uri)` или больше. `NULL` с размером 0 запрашивает только
длину.

### Текст

```c
const uint8_t *text;
size_t         text_len;
char           lang[64];
bool           utf16;
if (pn5180_ndef_extract_text(rec, &text, &text_len, lang, sizeof(lang), &utf16)) {
    /* text points into the record: text_len bytes, not NUL-terminated */
}
```

Текст не копируется: `text` указывает в полезную нагрузку (payload). Код языка копируется в `lang` и завершается NUL;
его длину задаёт карта, до 63 байт, так что в 64 байта помещается любой код, а в буфер поменьше — обрезанный. `utf16`
отличает UTF-16 от UTF-8; `lang` может быть `NULL`, как и `utf16`.

### Smart Poster

Smart Poster несёт в своей полезной нагрузке собственное сообщение: URI, заголовки на нескольких языках, действие,
значок.

```c
pn5180_ndef_record_t inner[8];
size_t n = pn5180_ndef_decode_smartposter(rec, inner, 8);
for (size_t i = 0; i < n; i++) {
    /* pn5180_ndef_extract_uri(&inner[i], ...), pn5180_ndef_extract_text(&inner[i], ...) */
}
```

Вложенные записи указывают в полезную нагрузку `rec`. Функция возвращает 0, если вложенное сообщение построено
неверно, содержит фрагментированные записи или содержит больше записей, чем вмещает массив.

## Сборка сообщения

```c
pn5180_ndef_record_t  records[2];
pn5180_ndef_message_t message;
uint8_t               text_payload[64];
uint8_t               uri_payload[128];

pn5180_ndef_message_init(&message, records, 2);

pn5180_ndef_record_t rec;
pn5180_ndef_make_text_record(&rec, "en", (const uint8_t *)"Hello NFC", 9, false, text_payload, sizeof(text_payload));
pn5180_ndef_message_add(&message, &rec);
pn5180_ndef_make_uri_record(&rec, "https://www.example.com", true, uri_payload, sizeof(uri_payload));
pn5180_ndef_message_add(&message, &rec);
```

- `pn5180_ndef_message_init()` отдаёт сообщению массив записей вызывающего; `pn5180_ndef_message_add()` копирует в
  него запись (саму запись, а не её данные) и возвращает `false`, если массив заполнен.
- `pn5180_ndef_make_text_record()` записывает полезную нагрузку — байт состояния, код языка и текст — в переданный
  буфер, которому нужно `1 + strlen(lang) + text_len` байт; код языка — не больше 63 байт.
- `pn5180_ndef_make_uri_record()` записывает полезную нагрузку в переданный буфер, которому нужно `1 + strlen(uri)`
  байт; с `abbreviate` самый длинный известный префикс заменяется своим кодом.
- `pn5180_ndef_make_mime_record()` и `pn5180_ndef_make_external_record()` копируют тип в `type_buf` (NUL не нужен, не
  больше 255 байт), а полезной нагрузкой делают `data`, без копирования.
- `pn5180_ndef_record_init()` заполняет запись с любым TNF по указателям вызывающего.

Каждый буфер, на который указывает запись, должен оставаться действительным, пока сообщение не закодировано или не
записано.

### Кодирование

```c
size_t size = pn5180_ndef_encode_message(&message, NULL, 0);   /* size query */
uint8_t *bytes = malloc(size);
size_t written = pn5180_ndef_encode_message(&message, bytes, size);
```

`pn5180_ndef_encode_message()` ставит флаги Message Begin и Message End и выбирает короткие записи там, где это
позволяет полезная нагрузка. Она возвращает число записанных байт, а при `out`, равном `NULL`, — нужное число; 0, если
сообщение пустое, буфер слишком мал или в сообщении есть запись, которую отверг бы разбор: запись Empty с типом, ID
или полезной нагрузкой, запись Unknown с типом, TNF Unchanged или Reserved, длина без своего указателя. При ошибке
ничего не записывается.

## Запись на метку

```c
pn5180_ndef_record_t  record;
pn5180_ndef_record_t  storage[1];
pn5180_ndef_message_t message;
uint8_t               payload[128];

pn5180_ndef_make_uri_record(&record, "https://www.example.com", true, payload, sizeof(payload));
pn5180_ndef_message_init(&message, storage, 1);
pn5180_ndef_message_add(&message, &record);

/* card: selected, after detect_card_type_and_capacity(). The data area is found on the tag. */
pn5180_ndef_result_t result = pn5180_ndef_write_card_auto(proto, card, &message);
```

`pn5180_ndef_write_card_auto()` — пара к `pn5180_ndef_read_card_auto()`: она записывает метки Ultralight / NTAG и
ISO15693 и возвращает `PN5180_NDEF_ERR_UNSUPPORTED` для карт MIFARE Classic и ISO14443-4. Порядок действий тот же,
что в библиотеке NXP для считывателей:

1. Capability container должен показывать поддерживаемую версию и доступ на чтение и запись, а в области данных
   должен быть NDEF TLV, на новой метке — пустой. Метки NTAG и ICODE обычно приходят с завода уже так
   отформатированными.
2. Сообщение заменяет содержимое этого TLV; TLV перед ним, например Lock Control TLV у NTAG, сохраняются.
3. Сначала длина TLV ставится в 0, а в самом конце — в настоящее значение, так что прерванная запись оставляет пустое
   сообщение, а не повреждённое.
4. За сообщением идёт Terminator TLV, если для него есть место в области данных.

| Результат | Значение |
| --------- | -------- |
| `PN5180_NDEF_OK` | записано |
| `PN5180_NDEF_ERR_NO_NDEF` | метка не отформатирована под NDEF: нет capability container или нет NDEF TLV |
| `PN5180_NDEF_ERR_READ_ONLY` | capability container не даёт доступа на запись |
| `PN5180_NDEF_ERR_CARD_FULL` | сообщение не помещается в область данных |
| `PN5180_NDEF_ERR_UNSUPPORTED` | тип карты, который эта функция не записывает, неизвестная версия схемы размещения, условия доступа, определённые производителем, или метка Type 2 с байтами блокировки или зарезервированными байтами внутри записываемых блоков |
| `PN5180_NDEF_ERR_READ_FAILED`, `PN5180_NDEF_ERR_WRITE_FAILED` | карта отвергла команду; выберите её снова |

Чтение обходит байты блокировки и зарезервированные байты метки Type 2, а запись нет: такая запись отклоняется. В этом
случае запишите блоки сами через `block_write`.

## Сообщения в памяти

Для данных, которые пришли не с метки через `pn5180_ndef_read_card_auto()`, например для сообщения, полученного по
другому каналу:

- `pn5180_ndef_parse_message()` разбирает закодированное сообщение в `pn5180_ndef_message_parsed_t`, который владеет
  его копией, с собранными фрагментированными записями; освобождается он через `pn5180_ndef_free_parsed_message()`.
- `pn5180_ndef_decode_message()` декодирует в массив вызывающего и ничего не выделяет; записи указывают во входные
  данные, а фрагменты остаются отдельными записями. Она возвращает 0 для неверно построенного сообщения или для
  сообщения, в котором записей больше, чем вмещает массив.
- `pn5180_ndef_decode_next()` декодирует одну запись по смещению и сдвигает смещение дальше — чтобы проходить
  сообщение запись за записью.
- `pn5180_ndef_tlv_find_ndef()` (`pn5180-ndef-tlv.h`) находит NDEF TLV в байтах области данных метки: она возвращает
  смещение и объявленную длину сообщения; сообщение может выходить за конец переданных байт, и это проверяет
  вызывающий.

Обе функции разбора проверяют структуру сообщения: Message Begin только на первой записи, Message End на последней,
после неё ничего, правильные последовательности фрагментов.

`pn5180_ndef_read_from_selected_card()` устарела: она читает сырые блоки начиная с заданного блока, и ей нужно
расположение данных на карте, которое знает `pn5180_ndef_read_card_auto()`. Со страницы 4 метки Type 2 и блоками по
16 байт она возвращает любое сообщение длиннее первого чтения повреждённым.
