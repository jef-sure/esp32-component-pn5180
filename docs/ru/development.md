# Разработка

*[In English](../en/development.md)*

Для тех, кто меняет драйвер: устройство репозитория, сборка примеров с ним, тесты на компьютере (host tests) и
документация.

## Репозиторий

| Путь | Что это |
| ---- | ------- |
| `include/pn5180.h` | слой считывателя: SPI, устройство, поле, радиообмен, регистры, EEPROM, LPCD; интерфейс протокола |
| `include/pn5180-14443.h`, `src/pn5180-14443.c` | ISO14443A: опрос, выбор, типы карт, остановка, аутентификация MIFARE; ISO14443-4 |
| `src/pn5180-apdu.c` | утилиты APDU, объявлены в `pn5180-14443.h` |
| `include/pn5180-15693.h`, `src/pn5180-15693.c` | ISO15693: инвентаризация, выбор, блоки, системная информация |
| `include/pn5180-mifare.h`, `src/pn5180-mifare.c` | READ и WRITE MIFARE, блоки значения |
| `include/pn5180-ndef.h`, `src/pn5180-ndef.c` | записи и сообщения NDEF: построение, кодирование, разбор |
| `src/pn5180-ndef-auto.c` | NDEF на метках: Type 2, MIFARE Classic, Type 4, Type 5 |
| `include/pn5180-ndef-tlv.h`, `src/pn5180-ndef-tlv.c` | поиск NDEF TLV |
| `include/pn5180-internal.h` | тайм-ауты, отладочный лог и вспомогательные функции, общие для исходников; не публичный |
| `src/pn5180.c` | слой считывателя |
| `examples/` | `simple_main`, `app_logic`, `ndef` |
| `host_test/` | тесты на компьютере, без железа |
| `docs/en/`, `docs/ru/` | эта документация |
| `CHANGES.md` | список изменений |

Код протоколов обращается к PN5180 только через функции `pn5180.h`, прежде всего через `pn5180_rf_transceive()`. На
этой границе и работают тесты на компьютере: первая тестовая программа заменяет `src/pn5180.c` и имитирует карты за
ним, вторая запускает `src/pn5180.c` с моделью чипа.

## Сборка примеров

Внутри репозитория примеры собираются с самим репозиторием, как бы ни назывался его каталог; менеджер компонентов для
них выключен:

```sh
. ~/esp/esp-idf/export.sh          # or the activation script of your ESP-IDF installation
idf.py -C examples/simple_main set-target esp32
idf.py -C examples/simple_main build
idf.py -C examples/app_logic set-target esp32s3
idf.py -C examples/app_logic build
```

`-B <directory>` кладёт сборку в другое место, так что рядом могут жить сборки под несколько версий ESP-IDF. Компонент
собирается с ESP-IDF 5.0.4 и новее, включая 6.x. Его публичные зависимости — `driver` и, начиная с ESP-IDF 5.3,
`esp_driver_spi` и `esp_driver_gpio`, потому что `pn5180.h` включает `driver/gpio.h` и `driver/spi_master.h`.

## Тесты на компьютере

`host_test/` собирает две программы для компьютера и запускает их под AddressSanitizer и UndefinedBehaviorSanitizer:

- **`pn5180_host_test`**: код протоколов (ISO14443, ISO15693, MIFARE, APDU, NDEF), где `src/pn5180.c` заменён на
  `host_test/fake_pn5180.c`, который отвечает на `pn5180_rf_transceive()` за имитируемые карты
  (`host_test/sim_cards.c`): NTAG, Ultralight C, MIFARE Classic, карту ISO14443-4 с приложением Type 4, метку ISO15693.
- **`pn5180_chip_test`**: сам слой считывателя `src/pn5180.c` с заглушками SPI master, GPIO, `esp_timer` и семафоров
  ESP-IDF (`host_test/stubs/`), за которыми стоит модель хост-интерфейса PN5180 (`host_test/chip_sim.c`: команды,
  BUSY, регистры, EEPROM, поле).

```sh
make -C host_test test IDF_PATH=<path to esp-idf>
```

Исходники Unity берутся из копии ESP-IDF или из отдельной копии Unity с `UNITY_DIR=<path to Unity/src>`. На GitHub
тесты при каждом push и pull request запускает workflow
[`.github/workflows/host-test.yml`](../../.github/workflows/host-test.yml).

Тесты проверяют опрос (в том числе поля со множеством карт), выбор, определение типа карты, чтение NDEF для всех
четырёх схем размещения и запись для Type 2 и Type 5, цепочки блоков ISO14443-4 и восстановление после потерянных
кадров, операции с блоками значения MIFARE, а также карты, которые ведут себя неправильно (карту, которая не слушается
HLTA; карту, которая отвечает пустыми блоками цепочки; карту MIFARE Classic, которая не отвечает на часть
аутентификаций; карту Type 4, в ответах которой на SELECT нет слова состояния). Для слоя считывателя проверяются кадры
SPI и обмен по линии BUSY, загрузка и проверка прошивки, проверка пинов, поле и защита от столкновения полей (RFCA),
то, как `pn5180_rf_transceive()` переводит состояние приёмника в свои результаты, значения Timer1 для тайм-аута
приёма, статус аутентификации MIFARE, восстановление, запись в EEPROM, пин IRQ и длительность ожиданий драйвера.

Модель ведёт себя так, как PN5180 описан в его техническом описании; для настоящих временных характеристик RF и
настоящих карт по-прежнему нужно железо.

Новое поведение кода протоколов получает тест с имитируемой картой в `host_test/test_main.c`, новое поведение слоя
считывателя — тест с моделью в `host_test/test_chip.c`.

## Стиль кода

Форматирование задаёт `.clang-format` в корне. Публичные имена начинаются с `pn5180_` и `PN5180_` и пишутся в
snake case. Пределы, которые программе может понадобиться изменить, — параметры функций `..._init()`, а не макросы
времени сборки.

## Документация

Документация — это Markdown, который одинаково читается на GitHub и на
[jef-sure.github.io](https://jef-sure.github.io/), где она публикуется из последнего выпуска:

- `README.md` и `README.ru.md`: что это за компонент, быстрый старт, карта страниц;
- `docs/en/*.md` и `docs/ru/*.md`: страницы, с одинаковыми именами файлов на обоих языках;
- `examples/*/README.md`: по странице на каждый пример.

Ссылки между страницами относительные, поэтому они работают в репозитории, в архиве компонента и на сайте. Изменение
поведения меняет и страницу, которая его описывает.

## Архив компонента

`idf_component.yml` перечисляет, что попадает в архив ESP Component Registry: исключено всё, а файлы компонента,
примеров и документации включены по шаблонам имён. Новый вид файла (`Kconfig`, исходник `.cpp`, картинка в `docs/`)
не попадает в архив, пока его не добавят в `include`. Тесты на компьютере, конфигурация CI и настройки редактора в
архив не попадают.
